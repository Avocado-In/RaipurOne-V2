# Supabase schema guide

The Phase 3 schema uses Supabase Auth for identity and stores application profiles in `public.profiles`. The backend uses the service-role key server-side; browser clients must never receive it.

## Main entities

Profiles, departments, workers, complaints, complaint images, ratings, notifications, assignment history, audit logs, and Telegram update idempotency records are included. Complaint records preserve the API's legacy fields while adding source, Telegram, location, and lifecycle data.

## Security

All application tables have RLS enabled. Citizen ownership and staff roles are enforced through `auth.uid()` and `app_metadata` role claims. Do not use editable `user_metadata` for authorization. Production deployments must review Storage object policies and run Supabase security advisors.

## Import order

1. Run `schema.sql` in a Supabase project.
2. Create Auth users and assign role claims through trusted server-side admin tooling.
3. Run `seed.sql`.
4. Verify Data API exposure, RLS behavior, Storage access, and indexes.

## Storage

Complaint images use the private `complaint-images` bucket. Store only object paths in `complaint_images`; signed URLs should be generated by the backend.
